## The LearningGraph Schema

Before populating a knowledge graph with data, we must define its *schema*—the vocabulary of permissible node types, edge types, and their constraints. This schema serves the same role as a database schema in relational systems: it specifies what assertions are well-formed and enables both validation and inference.

Table XX presents the LearningGraph schema. Each row defines an edge type with its source and target node types, plus any edge properties.

| Edge Type | Source | Target | Property | Semantics |
|-----------|--------|--------|----------|-----------|
| `has_skill` | Learner | Skill | proficiency | Learner's current level (0–4) |
| `requires_skill` | Work Role | Skill | proficiency | Minimum level for the role |
| `prerequisite` | Skill | Skill | — | Conceptual dependency |
| `teaches` | Course | Skill | proficiency | Maximum level the course develops |
| `skill_in_competency` | Skill | Competency | — | Skill belongs to competency area |

**Table XX:** LearningGraph edge schema. The five edge types connect six node types (Learner, Skill, Work Role, Course, Competency) with explicit constraints on valid source–target pairings.

Notice that proficiency appears in three edge types but with different semantics:

- For `has_skill`, proficiency is a *current state*—where the learner stands now
- For `requires_skill`, proficiency is a *threshold*—the minimum acceptable level
- For `teaches`, proficiency is a *ceiling*—the maximum level the course can develop

The `prerequisite` edge carries no proficiency property. This is a deliberate design choice: conceptual dependencies between skills are stable regardless of proficiency level. Programming is prerequisite to Feature Engineering whether a learner aims for basic competency or expert mastery. Proficiency requirements, by contrast, are context-dependent and handled by the role-specific `requires_skill` edges.

This separation of concerns—conceptual structure versus proficiency thresholds—simplifies the graph while preserving its utility for gap analysis and path planning.

### Temporal Considerations

The LearningGraph as presented is a *snapshot*: it captures the state of learners, courses, and requirements at a moment in time. A production learning management system would need to address temporal dynamics—how the graph evolves as learners complete courses, as skill requirements change, and as new content becomes available.

Such systems typically enforce temporal invariants. For example, demonstrated proficiency should not decrease: if a learner has shown level-3 competency in a skill, subsequent snapshots should reflect at least that level (barring explicit reassessment). We leave temporal extensions as an exercise, noting only that the snapshot model suffices for illustrating graph algorithms and analysis techniques.
